Keyboard & dialog issues

Found by tabbing through each screen and observing dialog behavior. Automated scanners do not catch these fully.

serious WCAG 2.4.3 Focus Order (A) · 4.1.2 Name, Role, Value (A)

Cookie banner leaves cover page fully interactive underneath

On first load the OneTrust consent dialog sits over the Demo Player cover, but axe still finds every cover control (identity picker, Contact me, Policies) and Tab can leave the banner into the page behind it. Screen-reader users can browse and activate controls that are visually obscured.

Evidence. First Tab stop was <button> — Contact me. 14 product elements were still audited under the banner (OneTrust itself was excluded from the axe scan).

Fix. Ensure the consent dialog traps focus, marks the page behind it inert/aria-hidden, and restores focus to the first cover control after Accept/Reject.
OneTrust banner integration on Demo Player cover
serious WCAG 2.4.3 Focus Order (A)

Opt-in dialog focus management needs a keyboard pass

Selecting a known viewer opens an Opt-in dialog over the cover. Confirm that focus moves into the dialog, Tab cycles within it, Escape dismisses (or is intentionally disabled), and focus returns to the trigger after Opt-in and Continue.

Evidence. First Tab stop after the dialog opened: <button> — Opt-in and Continue.

Fix. Use a focus trap on the Opt-in surface and set initial focus on the primary action or dialog title.
Demo Player cover · Opt-in modal
moderate WCAG 2.1.1 Keyboard (A) · 4.1.2 Name, Role, Value (A)

Video player keyboard & naming sweep

The in-player chrome exposes Pause/Mute/Subtitles/Settings/Fullscreen, reactions, Invite, sidebar demos, and Get in touch. Several controls rely on visible text; icon-only or compound labels still need verification against a screen reader.

Evidence. Of 16 Tab stops sampled in the player, 0 had no accessible name.

Fix. Give every icon control a stable aria-label, announce Now Playing changes via a polite live region, and keep captions discoverable from the keyboard.

Method & limits

Headless Chromium (Playwright) loaded https://play.goconsensus.com/be2376b21 at 1440×900 with a 2× pixel ratio. axe-core 4.12.1 ran against WCAG 2.1 A/AA + axe best practices on each screen. For every failure the element was scrolled into view, ringed, and captured with 48px of surrounding context. A separate pass tabbed up to 24 stops per screen.

Excluded. OneTrust cookie banner / preference center nodes were excluded from axe so the report reflects Consensus Demo Player UI, not the CMP vendor.

Limits. Guest “I’m new here” is blocked (“Sharing restricted for this demo”), so the lead form and Request Access path were not audited end-to-end. Invite, Comment, Settings menus, and caption tracks need a VoiceOver/NVDA pass. Focus-indicator visibility and some contrast on media are inconclusive from automation alone.
